사내망에서도 Claude Code나 Cline 같은 코딩 도구를 내부 모델에 연결해 쓰고 싶었다. 코드를 읽고, 수정하고, 실행 결과를 보면서 다음 작업을 이어가는 환경을 만드는 일이었다.

처음에는 모델 앞에 API를 하나 맞춰 주면 될 줄 알았다. 실제로 요청을 보내고 답을 받는 것까지는 가능했다. 그런데 사용하다 보면 다른 문제가 나왔다. 답변이 한참 뒤에 몰려 나오거나, 도구를 실행해야 할 차례에 아무 말 없이 끝나거나, 취소한 요청이 서버에서는 계속 돌고 있었다.

이 글은 그 사이에 만든 게이트웨이와 운영 포털의 기록이다. 2026년 6월 10일부터 11월 12일까지, 내부 모델을 코딩 도구에 연결하고 여러 사람이 함께 쓰는 서비스로 다듬은 과정을 정리했다.

## 시작은 ‘사내망에서도 코딩 에이전트를 쓰자’였다

외부 API로 사내 코드와 문서를 보내기 어려운 환경에서는 모델을 내부에 띄우는 것부터 필요하다. 모델 실행은 vLLM이 맡았다. vLLM은 GPU 위에서 모델을 실행하고, 다른 프로그램이 요청할 수 있도록 API를 제공하는 추론 서버다.

여기에 코딩 도구를 연결하려니 맞춰야 할 것이 생겼다. Claude Code는 Anthropic Messages 형식을 쓰고, OpenAI 호환 방식으로 연결하는 도구도 있었다. 같은 모델을 쓰더라도 클라이언트가 보내는 요청과 기대하는 응답이 달랐다.

사용자가 늘면 연결 문제에 더해 운영 문제도 생긴다. 누가 사용할 수 있는지, 키를 어떻게 발급할지, 특정 사용자의 요청이 왜 실패했는지 확인할 곳이 필요했다. 그래서 모델 앞에 **클라이언트를 연결하는 게이트웨이**, 그 옆에 **사용자와 사용량을 관리하는 포털**을 뒀다.

처음부터 필요한 일을 정리하면 다음과 같았다.

| 필요했던 것 | 서비스에서 맡은 일 |
| --- | --- |
| 익숙한 코딩 도구로 내부 모델 사용 | Anthropic·OpenAI API 연결과 클라이언트별 호환 처리 |
| 여러 사람이 같은 GPU 서버 사용 | 사용자별 API 키, 요청 빈도·동시 요청 제어 |
| 문제가 생겼을 때 원인 확인 | 요청 시간·토큰 사용량·오류 기록, 운영 화면 |
| 사내망에서 설치하고 유지 | 게이트웨이·포털의 외부 패키지 의존성을 줄인 구성 |

### 코딩 에이전트의 요청은 채팅 한 번으로 끝나지 않는다

예를 들어 “이 오류를 고쳐 줘”라고 입력하면, 모델은 곧바로 답을 완성하기보다 파일을 읽거나 명령을 실행해 달라고 요청할 수 있다. 도구를 실행한 결과가 다시 모델로 들어가고, 모델은 그 결과를 보고 다음 행동을 정한다.

파일 읽기나 명령 실행은 코딩 클라이언트 쪽에서 수행한다. 게이트웨이는 그 사이의 요청과 응답을 전달한다. 여기서 도구 이름이나 인자, 작업 종료 신호가 어긋나면 다음 단계로 넘어가지 못한다.

![사용자 지시 뒤 모델의 도구 요청, 클라이언트의 실행, 결과 재전송이 반복되는 코딩 에이전트의 흐름](/tech-b-log/images/llm-agent-cycle.svg)

여기서 토큰은 모델이 문장을 나눠 처리하는 단위이고, 컨텍스트는 한 번의 호출에 함께 들어가는 대화·파일·실행 결과 등의 문맥이다.

이 때문에 요청 수를 사람이 입력한 질문 수로 읽으면 안 된다. 한 번의 작업 안에서도 모델 호출이 여러 번 이어진다. 작업이 길어질수록 이전 대화와 실행 결과도 함께 보내므로 입력 길이가 커진다.

## 게이트웨이와 포털은 왜 따로 뒀나

요청이 지나가는 길은 짧게 뒀다. HTTPS 연결을 받은 뒤 게이트웨이가 인증과 요청 정책을 적용하고, 실제 모델 실행은 vLLM에 맡긴다. 포털은 이 경로 옆에서 계정·키·통계를 관리한다.

![HTTPS 프록시, 게이트웨이, vLLM으로 이어지는 요청 경로와 게이트웨이·포털이 공유하는 운영 DB의 관계](/tech-b-log/images/llm-service-architecture.svg)

게이트웨이와 포털은 Python 표준 라이브러리로 만들었다. 사내망에 새 패키지를 반입하고 의존성을 맞추는 일을 줄일 수 있는 구성이다. HTTP 서버, JSON 처리, SQLite까지 추가 패키지 없이 쓸 수 있었다. 모델 서빙에 필요한 GPU·CUDA·vLLM 환경은 별도로 관리했다.

계정·API 키·사용량 기록은 SQLite에 저장했다. 게이트웨이와 포털이 같은 DB를 공유하는 단일 서버 구성이어서 별도 DB 서버 없이 시작할 수 있었다. 읽기와 쓰기가 서로 덜 막히도록 WAL 모드를 쓰고, 스레드마다 연결을 따로 뒀다. WAL은 변경 내용을 별도 로그에 먼저 쓰는 SQLite의 동작 방식이다.

대신 직접 책임질 부분도 많았다. 표준 라이브러리 HTTP 서버를 쓴 만큼 스트리밍, 연결 재사용, 스레드 제한을 직접 다뤄야 했다. 실제로 뒤에서 설명할 지연 문제도 이 부분에서 나왔다. 패키지가 적다는 것만으로 운영이 단순해지지는 않았다.

포털을 나눈 이유도 역할이 달랐기 때문이다. 모델 호출에는 빠르고 일관된 전달이 필요하고, 운영 화면에는 사용자 승인, 키 발급·폐지, 사용량 조회, 로그 검색이 필요했다. 같은 DB를 보되 요청 처리와 관리 화면은 별도 프로세스로 뒀다.

## 처음에는 API를 번역했고, 나중에는 그 일을 덜어냈다

초기에는 Anthropic 형식의 요청을 게이트웨이에서 OpenAI 형식으로 바꾸고, vLLM의 응답을 다시 Anthropic 형식으로 돌려줬다. 내부 모델을 Claude Code에서 쓰기 위한 연결 부분이었다.

단순한 텍스트 대화보다 까다로운 부분은 도구 호출과 스트리밍이었다. 모델이 “이 도구를 실행해 달라”고 한 것인지, 작업을 마쳤다는 것인지, 답변이 중간에 잘린 것인지 구분해서 전달해야 했다. 추론 내용과 최종 답변, 토큰 사용량도 각각 맞춰야 했다.

| 시기 | Claude Code 요청이 지나가는 방식 | 게이트웨이가 책임진 범위 |
| --- | --- | --- |
| 초기 | Anthropic → OpenAI → Anthropic 변환 | API 형식 변환과 서비스 운영 정책 |
| 네이티브 API 전환 후 | vLLM의 Anthropic API 사용 | 인증·제한·전처리와 필요한 호환 보정 |

vLLM 0.32.0의 네이티브 Anthropic API로 전환하면서 양쪽 형식을 번역하는 부분을 제거했다. 백엔드가 직접 제공하는 형식을 활용하고, 게이트웨이에는 서비스에 필요한 일을 남기는 쪽으로 정리했다.

그렇다고 호환성 문제가 모두 사라지는 것은 아니었다. 클라이언트의 도구 사용 방식, 모델의 출력 방식, vLLM의 파서가 서로 맞아야 한다. Cline에서 겪은 빈 응답이 그 예다.

## 모델은 답을 만들었는데, 사용자는 아무것도 받지 못했다

Cline을 OpenAI 호환 모드로 연결한 특정 사용자의 요청에서 빈 응답이 많이 나왔다. 당시 분석한 요청 중 약 45%가 빈 응답이나 시간 초과 등으로 끝났다. 전체 서비스의 오류율과는 다른, 해당 사용자의 요청 집합에서 본 비율이다.

눈에 걸린 것은 출력 토큰 수였다. 토큰은 수십 개에서 수천 개까지 생성됐는데 클라이언트에는 답이 없었다. 모델이 생성하지 못한 것인지, 만든 결과가 전달되는 중에 없어졌는지부터 나눠 봐야 했다.

문제는 도구 호출 형식의 차이였다.

1. 당시 Cline의 GLM 연결은 시스템 프롬프트에 XML 형태의 도구 사용법을 넣었다. API의 `tools` 항목은 보내지 않았다.
2. 모델이 Cline이 기대한 XML 대신 GLM 고유 형식으로 도구 호출을 출력하는 경우가 있었다.
3. vLLM의 `glm47` 파서가 이를 도구 호출로 해석했지만, 요청에 도구가 선언되지 않아 결과를 버렸다.
4. 모델은 토큰을 생성했고 요청도 끝났지만, 클라이언트가 사용할 도구 호출은 남지 않았다.

![수정 전에는 선언되지 않은 도구 호출이 사라졌고, 수정 후에는 도구를 선언해 호출을 보존한 뒤 Cline용 XML로 돌려주는 흐름](/tech-b-log/images/llm-tool-bridge.svg)

게이트웨이에 이 경우를 위한 브리지를 추가했다. Cline 프롬프트에 있는 도구 정보를 읽어 vLLM 요청에 선언하고, 돌아온 도구 호출은 Cline이 읽는 XML 텍스트로 바꿨다. 이미 네이티브 `tools`를 보내는 요청에는 적용하지 않았다.

이 수정에는 비용과 한계도 있다. 도구 선언 때문에 입력이 약 700~900토큰 늘었고, 도구 호출을 XML로 돌려주는 시점은 해당 응답 생성이 끝난 뒤다. 프롬프트에서 알 수 없는 도구 이름까지 복원하는 것도 아니다.

실제 파서와 Cline의 응답 해석 방식을 연결한 재현 테스트에서는 35개 조합 중 수정 전 21개가 실패했고, 수정 후에는 35개가 통과했다. **이 결과는 재현 환경의 검증이다. 실제 GPU와 Cline 확장, 운영 트래픽에서의 개선 비율은 별도로 확인해야 한다.** 당시 변경 기록에도 그 확인이 남아 있다.

빈 응답을 추적하려면 HTTP 200만으로 성공을 판단할 수 없었다. 통신은 성공해도 답변이 없을 수 있기 때문이다. 사용량 기록에 빈 응답, 추론만 있는 응답, 출력 한도 도달 여부를 따로 남기도록 보완했다.

## 답변이 늦는 이유가 항상 모델에 있지는 않았다

스트리밍에서도 비슷한 일이 있었다. 스트리밍은 모델이 만든 답을 작은 조각으로 바로 보내서, 사용자가 전체 생성이 끝나기 전부터 읽을 수 있게 하는 방식이다. 그런데 게이트웨이를 거치면 한동안 멈춰 있다가 답이 몰려 나오는 문제가 있었다.

원인은 읽기 방식이었다. 중간에서 응답을 **4KB가 찰 때까지 모아 읽고 있었다.** 사용한 HTTP 라이브러리의 `read(4096)`은 chunked 응답을 그만큼 모으거나 응답이 끝날 때까지 기다렸다. 짧은 답변이라 전체가 4KB보다 작으면 생성이 끝날 때까지 전달이 밀릴 수 있었다.

모델은 조각을 보내고 있었는데 게이트웨이가 붙들고 있던 셈이다. 도착한 만큼 읽는 `read1()` 방식으로 바꾸고, 클라이언트에도 HTTP/1.1 chunked 응답으로 전달하도록 고쳤다.

아래는 일정한 간격으로 데이터를 보내는 가짜 추론 서버로 재현한 결과다. 40토큰을 50ms 간격으로 보내는 약 2초짜리 응답을 사용했다.

![로컬 재현 테스트의 Anthropic 스트리밍 완료 시간이 수정 전 35.15초에서 수정 후 2.01초로 바뀐 비교. 실제 모델 성능 측정이 아님](/tech-b-log/images/llm-stream-benchmark.svg)

수정 후에는 조각이 생성 간격에 맞춰 도착했고, 이 테스트에서 토큰 누락도 없었다. 위 수치는 실제 모델을 더 빨리 추론하게 만든 결과가 아니라, **전달 경로에서 생긴 지연을 재현하고 제거한 결과**다.

연결을 재사용하는 keep-alive도 함께 적용했다. 다만 keep-alive 자체의 루프백 측정 이득은 요청당 약 0.45ms였다. 수십 초의 차이를 keep-alive 덕분이라고 설명하면 맞지 않는다. 스트림을 제때 읽고 전달하는 문제가 핵심이었다.

### 연결을 오래 살려 두니, 가려져 있던 버그도 보였다

keep-alive 적용 과정에서는 SQLite 쓰기 실패 뒤 롤백이 빠진 경로도 확인했다. 실패한 트랜잭션이 쓰기 잠금을 놓지 않아 다음 로그 저장까지 기다리게 했다. 요청마다 스레드가 끝날 때는 연결도 정리되면서 가려졌지만, 연결과 스레드가 오래 살아남자 문제가 드러났다.

실패 시 롤백하도록 고쳤다. 같은 재현 조건의 논스트리밍 요청은 약 11.06초에서 1.4ms로 돌아왔다. 이것도 모델 추론 벤치마크가 아니라, 잠금 대기를 유발한 오류 경로의 수정 전후 결과다.

동시 처리 제한도 다시 봤다. 스레드가 일을 마치기 전에 제한 슬롯을 반환하는 코드가 있어 설정한 한도가 실제로 작동하지 않았다. 슬롯을 스레드가 끝날 때 반환하도록 옮겼다. 연결 수명을 바꾸는 작업이 DB와 동시성 제어까지 이어졌다.

## 오래 걸리는 요청과 끝난 요청을 구분해야 했다

코딩 작업은 입력이 길어서 첫 출력까지 기다리는 시간이 길 수 있다. 반대로 출력이 나오기 시작한 뒤 한동안 아무것도 오지 않는 경우도 있다. 이 둘을 같은 시간 제한으로 다루면 긴 입력을 처리하는 정상 요청을 끊거나, 멈춘 요청을 너무 오래 붙들게 된다.

그래서 첫 출력을 기다리는 시간, 출력 도중 조용한 시간, 요청 전체 시간을 나눠 감시했다. 사용자가 작업을 취소하거나 연결을 끊으면 백엔드 연결도 종료하도록 했다. 화면에서는 끝났는데 GPU에서는 생성이 이어지는 일을 줄이기 위해서다.

이 과정에서 소켓 읽기에 주기적으로 타임아웃을 걸고 다시 읽는 방식도 문제가 됐다. 한 번 타임아웃 난 Python 소켓 스트림이 이후 읽기를 거부할 수 있었다. 모델이 다시 데이터를 보내도 이미 읽을 수 없는 상태였다. 현재 코드는 읽기와 시간 감시를 분리하고, 별도의 감시 스레드가 시간 초과나 클라이언트 종료를 확인해 연결을 중단한다.

재시도도 응답이 사용자에게 나가기 전인지가 중요했다. 중간까지 전달한 뒤 처음부터 다시 생성하면 사용자와 코딩 도구가 이미 받은 내용을 되돌릴 수 없다. 코드에서는 **첫 content를 보내기 전의 조건부 내부 재시도**로 범위를 제한했다.

## 사용량이 늘면서 보는 숫자도 달라졌다

초기에는 요청이 성공했는지와 총 사용량부터 봤다. 코딩 작업이 길어지면서 요청당 입력 길이, 긴 요청의 지연, 캐시 상태도 함께 보게 됐다.

6월과 11월을 비교하면 일평균 요청은 약 37배, 요청당 평균 입력은 약 19배가 됐다. 요청 건수와 한 요청의 크기가 함께 커진 것이다. 아래는 운영 집계의 두 시점을 비교한 값이다.

![6월과 11월의 일평균 요청, 요청당 평균 입력, 응답 시간 p95를 각각 독립적인 축으로 비교한 운영 지표](/tech-b-log/images/llm-operating-metrics.svg)

응답 시간의 **p95는 요청 100개 중 약 95개가 그 시간 안에 끝났다는 뜻**이다. 남은 5개 같은 느린 요청을 놓치지 않으려고 평균과 함께 봤다.

| 지표 | 6월 | 11월 / 최근 집계 |
| --- | --- | --- |
| 월 요청 수 | 11,699건 | 263,499건 |
| 일평균 요청 수 | 649건 | 23,954건 |
| 월 처리 토큰 | 6,150만 | 248억 |
| 요청당 평균 입력 토큰 | 5,008 | 93,393 |
| HTTP 상태 코드 기준 에러율 | 41.2% | 0.5% (최근 7일) |
| 응답 시간 p50 | 5,364ms¹ | 1,529ms |
| 응답 시간 p95 | 108초 | 17초 |
| 응답 시간 p99 | 296초 | 50초 |
| 분당 최대 요청 | 49건 | 143건 |
| 월 활성 사용자 | 25명 | 65~71명 |

¹ 6월 p50은 성공(200) 응답 기준이다. 전체 응답의 p50은 1,628ms지만, 오류가 약 41%인 시기여서 성공 요청의 응답 시간과 구분해야 한다. 11월 월간 수치는 11월 12일 자료 작성 시점까지의 집계이고, 에러율 0.5%는 최근 7일 기준이다.

기간 중 모델과 서빙 설정, 입력 길이, 사용자 작업도 바뀌었다. 따라서 이 표는 서비스의 운영 변화로 읽어야 한다. 특정 코드 수정 하나가 p95를 108초에서 17초로 만들었다는 뜻은 아니다. 앞에서 설명한 재현 테스트와 이 운영 수치를 나눠 적은 이유다.

또 이 표의 에러율에는 HTTP 200으로 끝난 빈 응답까지 모두 포함되는 것은 아니다. 통신 실패와 실제 답변의 문제를 함께 보려면 새로 추가한 응답 진단 기록도 확인해야 한다.

### 요청 수만으로는 부하를 설명하기 어려웠다

긴 입력을 처리할 때는 KV 캐시도 살펴야 했다. KV 캐시는 모델이 앞에서 읽은 내용을 매번 다시 계산하지 않도록 GPU 메모리에 보관하는 중간 계산값이다. 요청이 길어지거나 동시에 처리하는 요청이 많아지면 필요한 공간도 커진다.

피크 시간에는 KV 캐시 점유율이 설정값을 넘을 때 일부 대규모 자동화 작업을 제한하는 정책을 추가했다. 기본 임계값은 75%였다. 모든 요청을 막기보다 개발·디버깅에 쓰는 요청을 살리려는 운영 정책이었다.

다만 당시 구현은 등록한 키워드로 요청 종류를 구분하는 방식이다. 작업의 무게를 정확히 계산하는 스케줄러는 아니다. 이 한계를 알고 사용해야 했고, 순간적인 부하까지 즉시 반영하는 것도 아니었다.

자료 작성 시점의 서빙 구성은 GLM-5.3-Flash, GPU 8장, TP 8과 Expert Parallel·비동기 EPLB, MTP 5였다. 최대 입력·출력 컨텍스트는 약 100만 토큰이고, KV 캐시는 `fp8_ds_mla`를 사용했다. 이 구성의 비교 실험과 튜닝은 별도 글에서 다루는 편이 낫겠다. 여기서는 게이트웨이를 만들고 운영하면서 겪은 일에 집중했다.

## 아직 끝나지 않은 일

10월에는 트래픽이 약 3배 늘면서 에러율이 1.6%로 올라간 구간이 있었다. 해당 기간의 500 응답 6,068건은 원인 분석 대상으로 남아 있었다. 11월 p95도 17초라, 긴 입력을 보내는 작업에서는 기다림이 여전히 컸다.

다음에는 긴 요청이 어디에서 기다리는지, 반복되는 입력이 캐시에 얼마나 재사용되는지 더 세분해서 볼 필요가 있다. HTTP 요청이 끝났다는 기록과 코딩 작업이 제대로 이어졌다는 기록의 차이도 계속 살펴야 한다.

처음에는 API 형식을 연결하는 작업으로 시작했다. 운영해 보니 더 많은 시간을 쓴 곳은 응답이 지나가는 중간이었다. 답변을 모아 두던 읽기 방식, 없어져 버린 도구 호출, 끝나지 않은 DB 트랜잭션처럼 작아 보이는 동작이 사용 경험을 바꿨다.

그래서 지금은 요청 하나를 볼 때도 모델이 무엇을 만들었는지, 게이트웨이가 무엇을 전달했는지, 클라이언트가 그 결과로 다음 행동을 했는지를 나눠 본다. 이 서비스를 만들고 운영하면서 가장 자주 돌아가 확인하게 된 흐름이다.
