모델을 호출할 수 있는 환경에서, 코딩 도구가 지속적으로 사용할 수 있는 서비스로 발전시킨 과정입니다.

기록 범위: **2026년 6월 10일~11월 12일**

## 배경과 구성

폐쇄망에서 코딩 에이전트를 활용하려면 내부 추론 서버와 클라이언트 사이의 API 연결뿐 아니라, 도구 호출·스트리밍·오류 처리까지 실제 사용 흐름이 이어져야 합니다. 이 프로젝트에서는 Anthropic·OpenAI 호환 게이트웨이와 운영 포털을 구축하고, 약 5개월 동안 사용량과 요청 길이의 증가에 맞춰 서비스를 개선했습니다.

![코딩 클라이언트에서 SSL 프록시와 API 게이트웨이를 거쳐 vLLM으로 전달되는 요청 흐름](/tech-b-log/images/llm-service-flow.svg)

게이트웨이는 클라이언트 요청과 추론 서버를 연결하고, 포털은 사용량 통계와 로그 조회 등 운영 기능을 제공합니다. 초기 게이트웨이와 포털은 Python 표준 라이브러리로 구축했습니다.

> 이 글은 운영 기록을 바탕으로 구성한 사례 소개입니다. 내부 소스코드, 접속 주소와 포트, 사용자 입력 및 로그 원문은 포함하지 않습니다.

## 약 5개월의 개선 과정

### 6월 · 초기 구축과 요청 제어

Anthropic·OpenAI 호환 게이트웨이와 포털을 먼저 구축했습니다. 이후 동시 요청 수, 요청 시간, 응답 크기에 제한을 두고 클라이언트 연결 종료를 감지하도록 개선했습니다. 초기에는 기본 기능의 제공과 오류 대응에 집중했습니다.

### 7—8월 · 클라이언트별 호환성 개선

Claude Code의 첫 요청에서 발생하는 400·500 오류, 도구 호출 오류, reasoning만 반환되는 응답과 503 재시도 루프 등 클라이언트별 문제를 수정했습니다. 운영 기록의 에러율은 6월 약 41%에서 7월 0.9%, 8월 0.2%로 낮아졌습니다.

이 시기에는 모델과 NVIDIA 드라이버·CUDA·vLLM 환경을 전환하고, 통계 대시보드와 시스템 로그 검색, 주간 보고서 등 관측 기능도 확충했습니다.

### 9—11월 · 구조 개선과 지연 감소

설정을 외부화하고 SSE 스트리밍 처리를 정상화했으며, HTTP/1.1 keep-alive를 적용했습니다. 운영 기록에는 vLLM 직접 호출과 유사한 전송 동작을 확보한 것으로 정리되어 있습니다. 이 기간 p95는 8월 109초에서 9월 35초로 감소했습니다.

이후 vLLM의 네이티브 Anthropic API를 사용하도록 전환해 게이트웨이 번역 계층을 제거했습니다. Cline XML 도구 브리지는 시각화·병렬 요청 등에서 도구 호출이 실패하는 사례에 대응하기 위해 추가했습니다.

출력 예산 정책을 통일하고 빈 응답 진단, 스트리밍 감시와 content 전 내부 재시도를 추가했습니다. 이미지 입력과 프롬프트 전문 감사 기능 등 사용·운영 기능도 확장했습니다.

## 운영 지표의 변화

사용량뿐 아니라 요청당 입력 길이도 크게 증가했습니다. 아래 표는 초기 구축 시기와 11월 운영 집계를 비교한 결과입니다.

| 지표 | 6월 | 11월 / 최근 집계 |
| --- | --- | --- |
| 월 요청 수 | 11,699건 | 263,499건 |
| 일평균 요청 수 | 649건 | 23,954건 |
| 월 처리 토큰 | 6,150만 | 248억 |
| 요청당 평균 입력 토큰 | 5,008 | 93,393 |
| 에러율 | 41.2% | 0.5% (최근 7일) |
| 응답 시간 p50 | 5,364ms¹ | 1,529ms |
| 응답 시간 p95 | 108초 | 17초 |
| 응답 시간 p99 | 296초 | 50초 |
| 분당 최대 요청 | 49건 | 143건 |
| 월 활성 사용자 | 25명 | 65~71명 |

¹ 6월 p50은 성공(200) 응답 기준입니다. 전체 응답 기준 p50은 1,628ms지만 오류 비율이 약 41%로 높아 해석에 주의가 필요합니다. 11월 월간 수치는 문서 작성 시점까지의 누계이며, 에러율 0.5%는 최근 7일 집계입니다.

> 지표는 서비스 전체의 변화입니다. 기간 중 모델, 서빙 구성, 요청 길이와 트래픽이 함께 변했으므로 특정 수정 하나의 성능 효과로 해석하지 않습니다.

## 긴 컨텍스트에 대응하는 운영

요청이 급증하던 시기에는 KV 캐시 점유율 75% 초과 시 추론용 요청을 선택적으로 차단하는 피크 타임 게이트를 도입했습니다. 평균 입력이 약 9만 토큰으로 증가하면서 요청 건수와 함께 입력 길이와 캐시 상태를 살피는 것이 운영의 주요 과제가 되었습니다.

### 현재 추론 구성

- GLM-5.3-Flash · GPU 8장
- Tensor Parallel 8 + Expert Parallel + 비동기 EPLB
- MTP 5 · vLLM v0.32.0
- 최대 컨텍스트 1,048,576토큰 · KV 캐시 `fp8_ds_mla`

### 남아 있는 과제

10월에는 트래픽이 약 3배 늘면서 에러율이 1.6%로 소폭 상승했습니다. 해당 기간의 500 응답 6,068건은 원인 분석 대상으로 남아 있습니다.

11월 p95는 17초로 개선됐지만 긴 컨텍스트 요청이 지연의 긴 꼬리를 지배하고 있습니다. 다음 최적화 대상으로 캐시 히트율을 관리하며, 반복 입력의 재사용과 실제 요청 분포를 함께 확인할 필요가 있습니다.

## 기록의 기준

운영 DB의 요청·지연 집계와 변경 이력(v1.0—v3.2.6)을 요약한 2026년 11월 12일자 자료를 바탕으로 작성했습니다. 이 페이지에서는 결과와 변경 이력으로 확인할 수 있는 범위만 설명하며, 개별 변경의 인과 효과나 동일 조건의 벤치마크를 주장하지 않습니다.
